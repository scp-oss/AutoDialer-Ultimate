# AutoDialer Ultimate — статус проекта и план дальнейшей разработки

Этот документ фиксирует, что было сделано в текущей фазе работ ("Phase 1:
рабочее ядро"), какие архитектурные решения приняты и почему, и что
остаётся для полного соответствия исходному техническому заданию
(промышленная система массового SIP-обзвона с веб-интерфейсом на React,
TTS/STT, Kubernetes-манифестами и т.д.).

## Как читать этот документ

Раздел 1 — что реально работает и проверено. Раздел 2 — архитектура как
она есть сейчас. Раздел 3 — что осталось сделать, по фазам. Раздел 4 —
как развернуть и проверить систему locally.

---

## 1. Phase 1: что сделано

Исходный репозиторий представлял собой результат минимум двух независимых
генераций кода, которые никогда не сводились воедино: плоский монолит
`backend/` (на который были заведены `docker-compose.yml`/CI) и
архитектурно более зрелый модульный пакет `app/`, который не запускался
вовсе — `app.create_app()` падал на первом же импорте.

Phase 1 состояла в том, чтобы (а) выбрать `app/` как единственное ядро
(б) довести его до реально работающего состояния (в) связать с
Docker/Alembic/CI (г) добавить то, что было объявлено, но не
реализовано (WebSocket-дашборд) (д) проверить весь стек end-to-end
насколько позволяет среда выполнения.

### 1.1 Исправленные баги (по серьёзности)

Каждый пункт был найден и подтверждён через реальный запуск кода
(`python -c "import app"` → `pytest` → живой Postgres/Redis/Asterisk),
а не только чтением исходников.

**Критичные (ломали основную функциональность полностью):**

1. **AMI-команды никогда не работали.** `app/services/dialer.py` строил
   каждый AMI-запрос (подписку на события, `Originate`, `Hangup`,
   `Ping`, `CoreShowChannels`) через `panoramisk.message.Action(...)` —
   такого класса в `panoramisk` не существует. Это `AttributeError` на
   **каждый** вызов, включая инициацию звонка — то есть обзвон в принципе
   не мог позвонить ни на один номер, при этом само AMI-соединение
   устанавливалось успешно и выглядело "живым". Заменено на `ami_action()`
   — обычный dict с ключом `Action`, как того требует реальный API
   `panoramisk.Manager.send_action()`. Подтверждено вживую: запущен
   настоящий Asterisk, AMI подключился, `Ping`/`Originate`-совместимые
   вызовы формируются корректно.
2. **`app/core/logger.py` не содержал логгер.** Файл фактически содержал
   код FastAPI-зависимостей (`get_current_user`, `require_admin`, rate
   limiting) — а не `StructuredLogger`, который импортирует весь
   остальной проект (`from app.core.logger import logger`). Переименован
   в `app/core/dependencies.py` (этому соответствует и его собственный
   docstring); `app/core/logger.py` написан заново — контекстные
   переменные (correlation/request/user id), JSON/console форматтеры,
   ротация файлов, `AuditLogger`, `LogTimer`.
3. **`app/utils/ami_manager.py` — мёртвый код.** Второй, неиспользуемый
   `DialerManager` (740 строк), при этом обёрнутый в
   `try/except ImportError`, из-за чего реальный `DialerManager` из
   `app/services/dialer.py` тихо подменялся заглушкой, кидающей
   `ImportError` при любом обращении. Удалён.
4. **`init_dialer()` блокировал старт приложения на ~5.5 минут**, если
   Asterisk недоступен (10 попыток подключения с exponential backoff
   `2..60`с) — при этом сам код был обёрнут в try/except, который никогда
   не успевал сработать вовремя для отдачи `/api/health` при недоступном
   SIP. Добавлен режим `quick=True` для стартового подключения (1 попытка)
   с последующим фоновым переподключением каждые 30с — веб-интерфейс и
   REST API теперь доступны сразу, даже если SIP ещё не настроен/недоступен
   (ровно то поведение, которого требует ТЗ: статусы Online/Offline/
   Registration failed, а не падающий бэкенд).
5. **`init_services()` не связывал модульные singletons.** Каждый сервис
   регистрировался в `ServiceRegistry`, но НЕ через `set_X_service()`,
   который используют свободные функции `get_X_service()`, вызываемые
   API-роутерами напрямую — то есть каждый эндпоинт при первом же запросе
   упал бы с `RuntimeError("... не инициализирован")`. Также
   `SystemService` создавался без ссылок на `dialer_manager`/
   `transcription_service`, из-за чего статус AMI/SIP в `/api/health`
   всегда показывал `not_initialized` независимо от реального состояния.
6. **JWT-токены не проходили собственную проверку.** `create_token()`
   подписывает токен с `aud=autodialer-api`, но `decode_token()` не
   передавал `audience=` в `jwt.decode()` — python-jose при наличии `aud`
   в токене требует явно передать ожидаемую аудиторию, иначе кидает
   `Invalid audience`. Итог: **ни один** выданный токен не декодировался
   бы обратно, то есть вход в систему был бы сломан после первого же
   запроса с токеном. Исправлено, покрыто тестом.
7. **`env_prefix="AUTODIALER_"` в `Settings`** делал недействующими ВСЕ
   переменные окружения, задокументированные в `.env.example`
   (`DB_HOST`, `JWT_SECRET`, `AMI_PASSWORD` и т.д. — без префикса).
   `.env`-конфигурация не подхватывалась вообще, всё тихо уходило на
   дефолты (включая небезопасный `SECRET_KEY` по умолчанию). Убран
   префикс; `SECRET_KEY` получил `validation_alias="JWT_SECRET"` для
   соответствия документации/docker-compose/скриптам.
8. **`sql/schema.sql`: триггер версионирования падал на каждой вставке
   в `settings`.** `create_record_version()` обращается к `NEW.id`, а
   PK таблицы `settings` — `key` (VARCHAR). 17 дефолтных настроек не
   могли быть вставлены ни при `docker-entrypoint-initdb.d`, ни через
   Alembic. Триггер `version_settings` убран (settings осознанно не
   версионируется по `id`).
9. **`asterisk/pjsip.conf.template` не парсился Asterisk 20** —
   `support_outbound` (в секции `aor`/`registration`) и
   `max_initial_qualify` (в `global`) не существуют как опции PJSIP;
   Asterisk отбрасывал объекты `aor`/`global` целиком при попытке их
   создать, что в конечном итоге ломало исходящую регистрацию
   (`AOR '' not found`). Подтверждено и исправлено на **реальном**
   Asterisk 20.6 — после фикса SIP REGISTER проходит полный цикл и
   `pjsip show registrations` показывает `Registered`.

**Существенные (ломали конкретные функции):**

10. 11 моделей ответов (`CampaignResponse`, `ContactResponse`,
    `UserResponse` и т.д.) объявляли `class X(BaseSchema, TimestampSchema)`
    — `TimestampSchema` сам наследует `BaseSchema`, это ошибка порядка
    MRO, `TypeError` при импорте.
11. `app/models/task.py`, `stats.py`, `api_token.py` — систематическая
    опечатка `description("текст")` вместо `description="текст"`
    (226 строк), плюс несколько строк с несбалансированными
    скобками.
12. `app/services/dialer.py`/`call_result.py` — два Prometheus-метрики
    регистрировались под одинаковым именем (`autodialer_active_calls`,
    `autodialer_call_duration_seconds`) → `ValueError: Duplicated
    timeseries` при импорте; аналогично `app/core/__init__.py` определял
    4 неиспользуемых метрики, коллизирующих с настоящими метриками в
    сервисах (Counter `..._total` автоматически резервирует и
    сопутствующее имя `..._created`).
13. `app/workers/metrics.py` создавал новый `Gauge(...)` при **каждом**
    вызове периодической функции — упал бы на второй итерации с той же
    ошибкой дублирования. Метрики вынесены на уровень модуля.
14. `app/services/transcription.py.get_info()` — синхронный метод
    вызывал `self.redis.llen(...)` (асинхронный) без `await`, кладя
    сам объект корутины в `queue_size`; воркер падал с
    `'>' not supported between instances of 'coroutine' and 'int'`
    на каждой проверке очереди транскрибации.
15. `app/__init__.py` регистрировал `loop.add_signal_handler(SIGTERM/
    SIGINT)` без обработки исключений — падает с `RuntimeError` вне
    главного потока главного интерпретатора (в частности, в тестах
    через Starlette TestClient).
16. `app/services/dialer.py.stop_all_calls()` обращался к
    `self.channels_hash_key`, которого не существует (опечатка/пропущенная
    инициализация) — `AttributeError` при остановке обзвона.
17. `start_all_workers()`/`stop_all_workers()` никогда не вызывались из
    `app/__init__.py` — все фоновые задачи (retry queue, транскрибация,
    health monitor, log cleanup) были определены, но не запускались.

### 1.3 Новое / реализованное с нуля

- **Alembic** (`alembic/`) поверх существующей асинхронной asyncpg-модели
  доступа к данным: `alembic/env.py` использует
  `sqlalchemy.ext.asyncio` + `asyncpg` только для управления миграциями
  (без ORM-моделей, рантайм по-прежнему работает через
  `app/core/database.py: ConnectionPool/QueryBuilder/BaseRepository`,
  см. §2.2 почему). Первая миграция `0001_initial_schema.py` применяет
  `sql/schema.sql` (23 таблицы, 90+ индексов, триггеры, функции,
  5 представлений, дефолтные данные) через собственный
  `$$...$$`-aware SQL-сплиттер (asyncpg не умеет multi-statement
  `execute()`). Проверено: `upgrade head` → `downgrade base` →
  `upgrade head` — полный цикл, идемпотентно.
- **WebSocket-дашборд** (`app/services/websocket.py` +
  `app/api/websocket.py`, эндпоинт `/api/ws/dashboard`): менеджер
  локальных соединений + подписка на Redis Pub/Sub
  (`ws_channels:{call,campaign,system,notification}`), чтобы события,
  сгенерированные в дозвонщике или в фоновом воркере (другой процесс),
  доходили до всех подключённых клиентов дашборда. Использует уже
  существовавшие, но нигде не применявшиеся Pydantic-модели
  `LiveCallEvent`/`CampaignProgressEvent`/`SystemNotificationEvent`
  (`app/models/system.py`). Проверено end-to-end тестом: клиент
  подключается, получает начальный снимок статуса, затем реальное
  сообщение, опубликованное в Redis из отдельного клиента.
- **`app/services/notification.py`** — CRUD поверх таблицы
  `notifications` + публикация в тот же WebSocket-канал.
- **Docker**: `Dockerfile` (backend, `python:3.12-slim`, entrypoint
  сначала гоняет `alembic upgrade head`), `docker/asterisk/Dockerfile` +
  `entrypoint.sh` (рендерит `pjsip.conf`/`manager.conf` из шаблонов через
  `envsubst`, поднимает Asterisk с нашим дозвонным контекстом),
  `docker-compose.yml` (postgres, redis, asterisk, backend, nginx;
  volumes для `tts_audio`/`call_recordings`, шаренные между backend/
  asterisk/nginx; healthchecks; обязательные секреты через
  `${VAR:?required}`).
- **CI** (`.github/workflows/tests.yml`): переписан на Python 3.11/3.12,
  `app/requirements/dev.txt`, реальные Postgres+Redis services,
  `alembic upgrade head` перед тестами, `ruff` (два прохода: строгий по
  `F821/F822/F823/E9` — падает сборку; полный — только предупреждение),
  `mypy` (advisory).
- **`tests/`** — новый набор (12 тестов, ранее отсутствовал): boot
  smoke-тесты, JWT/пароли (unit), health/liveness/readiness (интеграция
  с реальными Postgres+Redis, без падения при недоступном AMI),
  WebSocket (подключение + сквозная доставка через Redis Pub/Sub),
  регрессионный тест на `ami_action`.

### 1.4 Как это было проверено

Первую часть Phase 1 демон Docker был недоступен в рабочей среде (нет
доступа к cgroups/`/var/run/docker.sock`), поэтому вся валидация того
периода шла через **нативно установленные** PostgreSQL 16, Redis 7 и
Asterisk 20.6 (все три — через `apt`) с теми же самыми конфигами
(`sql/schema.sql` через Alembic, `asterisk/*.conf`/`pjsip.conf.template`
через тот же `envsubst`, что и в `docker/asterisk/entrypoint.sh`), только
на `127.0.0.1` вместо DNS-имён сервисов compose — этот путь по-прежнему
остаётся основным способом быстрой локальной проверки при разработке.

**В одной из последующих сессий Docker неожиданно оказался доступен**, и
`docker compose up --build` был прогнан по-настоящему — впервые с начала
проекта. Это сразу же вскрыло шесть реальных багов, ни один из которых не
проявлялся при нативной проверке, потому что она обходила ровно те пути
(Dockerfile-сборку, docker-compose сеть, реальный AMI поверх реального
Asterisk-контейнера), в которых эти баги жили:

1. `docker/asterisk/Dockerfile`: `apt-get install asterisk` вообще не
   имел кандидата на установку на `debian:12-slim` — Debian убрал пакет
   `asterisk` из архива полностью начиная с bookworm (остались только
   производные `asterisk-core-sounds-*`/`asterisk-prompt-*`, не сам
   демон). Базовый образ заменён на `ubuntu:24.04` — тот же
   `1:20.6.0~dfsg+~cs6.13.40431414-2build5`, что уже был провалидирован
   нативно, есть в `noble/universe` "из коробки".
2. Тот же Dockerfile: `chown ... /var/run/asterisk` падал, потому что
   каталог ещё не существовал в свежем минимальном образе (некому было
   создать его на этапе установки пакета — обычно это делает init-система
   при первом запуске сервиса, которой в контейнере без systemd нет).
3. `Dockerfile` (backend): никогда не копировал `sql/` в образ, хотя
   `alembic/versions/0001_initial_schema.py` читает `sql/schema.sql` в
   рантайме — на **любом** свежем контейнере первая же миграция падала
   с `FileNotFoundError`, то есть база вообще не создавалась.
4. `nginx/autodialer.conf`: захардкоженный `listen [::]:80` полностью
   ронял nginx (`socket() [::]:80 failed: Address family not supported`)
   на любом хосте/контейнере без поддержки IPv6 в сетевом namespace —
   частый случай для ограниченных Docker-хостов/CI. IPv6 никогда не был
   заявленным требованием проекта, поэтому directive просто убран.
5. `app/core/database.py: ConnectionPool.acquire()` — самый серьёзный из
   шести. Один общий `except Exception` оборачивал **всё** тело `async
   with db_pool.acquire()` вызывающего кода, а не только сам вызов
   `pool.acquire()` — то есть любое бизнес-исключение сервиса
   (`InvalidCredentialsError` при неверном пароле, любой `XNotFoundError`
   и т.д.), поднятое внутри блока, подменялось на
   `QueryError("Failed to acquire connection: ...")`, теряя и тип, и
   сообщение исходной ошибки. Вдобавок **нигде в проекте** не было ни
   одного обработчика, конвертирующего ~50 кастомных исключений сервисов
   в HTTP-ответ — любая бизнес-ошибка API (неверный пароль, "не найдено",
   валидация, конфликт) долетала до FastAPI необработанной и превращалась
   в голый `500 Internal Server Error` без единой полезной детали.
   Живой пример до фикса: `POST /api/auth/login` с неверным паролем → 500;
   после фикса → `401 {"detail": "Неверное имя пользователя или пароль"}`.
   Исправлено в двух местах: `acquire()` разделён на два `try/except` (не
   заворачивает бизнес-исключения), и добавлен глобальный
   `exception_handler` (`app/__init__.py`), сопоставляющий класс
   исключения с HTTP-статусом по суффиксу имени
   (`NotFoundError`→404, `AlreadyExistsError`/`DuplicateError`→409,
   `InvalidCredentialsError`→401, `ValidationError`→422 и т.д.; всё, что
   не относится к `app.services.*`, пробрасывается как есть, чтобы
   настоящие непредвиденные баги по-прежнему громко становились 500).
6. `app/services/dialer.py`: `_sync_channels_from_asterisk()` и
   `_check_channel_alive()` делали `response.events`, но panoramisk
   резолвит multi-response AMI-экшены (`CoreShowChannels`,
   `CoreShowChannel`) обычным `list`-ом объектов `Message`, а не объектом
   с атрибутом `.events` — `AttributeError` на **каждом** цикле
   реконсиляции/watchdog при реальном подключении к настоящему Asterisk
   по AMI (никогда не проявлялось раньше, потому что AMI никогда не был
   живым end-to-end). Добавлен `ami_response_events()`, нормализующий обе
   возможные формы ответа.

Седьмой баг того же раунда, найденный чуть позже при повторном живом
прогоне: `app/services/transcription.py: _process_transcription_queue()`
опрашивал очередь через `blpop(timeout=5)`, а таймаут сокета redis-клиента
(`REDIS_SOCKET_TIMEOUT`) по умолчанию **тоже** 5 секунд — при равных
значениях клиентский сокет-таймаут гонится с серверным graceful-нил от
`BLPOP` и почти всегда выигрывает гонку, так что при каждом опросе пустой
очереди (то есть почти всегда) прилетал `TimeoutError` вместо штатного
`None`. В логах это было видно как повторяющаяся каждые ~11 секунд ошибку
"Ошибка в обработчике очереди: Timeout reading from redis:6379".
Исправлено: таймаут `BLPOP` теперь всегда безопасно меньше таймаута
сокета (`REDIS_SOCKET_TIMEOUT - 2`, не ниже 1с).

**Все семь багов исправлены, покрыты регрессионными тестами
(`tests/test_error_handling.py`, `tests/test_dialer.py`) и проверены
живьём через полный `docker compose up` с нуля** (`docker compose down
-v` → `up`, наблюдение логов 90+ секунд без повторения ни одной из старых
ошибок): здоровый `/api/health` через backend напрямую и через nginx,
успешный `alembic upgrade head` (0001→0009) через entrypoint-скрипт
образа, полный цикл входа (неверный пароль → 401, верный → 200 с JWT),
404 на несуществующую кампанию, 409 на дублирующееся имя группы контактов,
реальное AMI-соединение с настоящим Asterisk-контейнером. Регрессия —
`pytest` 127/127. `docker-compose.yml`/`Dockerfile`/
`docker/asterisk/Dockerfile` теперь можно считать проверенными не только

**Критическая находка: живая обработка AMI-событий никогда не
работала — вообще, ни разу, за всю историю проекта.** Проверяя запрос
"нужен 100% рабочий проект — от установки до звонка и его принятия",
был размещён реальный тестовый звонок через тот же AMI Originate,
который использует `DialerManager.originate_call()`, и проверено, что
`call_results` действительно получает запись. Не получила — обнаружены
и исправлены четыре независимых, ранее никогда не всплывавших бага,
из которых первый — самый серьёзный баг во всём проекте на сегодня:

1. **`app/services/dialer.py: handle_ami_event()` читал
   `event_name = event.name`.** У `panoramisk.message.Message`
   (наследник `CaseInsensitiveDict`) нет атрибута `.name` —
   `__getattr__` молча возвращает `self.get('name', '')`, то есть
   всегда пустую строку, поскольку у AMI-события есть заголовок
   `Event:` (ключ `'event'`), а не `'name'`. Живьём проверено:
   `Message.from_line('Event: Hangup\r\n...').name == ''`, тогда как
   `.event == 'Hangup'`. Значит вся цепочка `if/elif` по
   `DialBegin`/`DialEnd`/`BridgeEnter`/`Hangup`/`UserEvent`/`DTMF`
   внутри `handle_ami_event()` никогда ни разу не сработала — AMI-
   события исправно приходили на TCP-соединение (это отдельно
   подтверждено сырым захватом трафика мимо panoramisk), но Python-код
   их просто не различал. Это ставит под сомнение и утверждение §3.4
   "живые события в WebSocket — сделано": `_publish_call_event(...)`
   внутри этих же обработчиков тоже никогда не вызывался. Исправлено:
   `event_name = event.get('event', '')`.
2. **`DialerManager.originate_call()` передавал переменные канала через
   заголовок AMI-экшена `'Setvar'`.** У современного Asterisk
   Originate-экшена нет параметра `Setvar` — переменные передаются
   через `'Variable'`. Поскольку Asterisk молча игнорирует неизвестные
   заголовки AMI-экшена вместо того, чтобы отклонить экшен, ответ на
   Originate всегда был `Success`, но `__CAMPAIGN_ID`/`__RETRY_COUNT`
   ни разу не попадали в реальный канал. Живьём проверено трассировкой
   `extensions.conf`: с `'Setvar'` — `Set(CAMPAIGN_ID=)` (пусто), с
   `'Variable'` — `Set(CAMPAIGN_ID=7)`. Исправлено на `'Variable'`.
3. **`asterisk/extensions.conf`: все `UserEvent(...)` использовали
   `Key=Value` вместо `Key: Value`.** Команда `asterisk -rx "core show
   application UserEvent"` прямо говорит: "The `<body>` may be specified
   as a ',' delimited list of **key:value** pairs" — Asterisk передаёт
   каждый через-запятую аргумент как отдельную AMI-строку заголовка
   буквально, не разбирая `=`. Строка вида `Status=busy` — не валидный
   AMI-заголовок (`Header: Value`), поэтому panoramisk (и любой другой
   корректный AMI-клиент) её просто не парсит как пару ключ/значение.
   Итог: `Status`/`Campaign`/`Phone`/`RetryCount`/`DTMF`/`Duration`/
   `BillSec` не существовали на Python-стороне ни для одного
   `DialerResult`/`DialerHangup`-события, никогда. Исправлено заменой
   `=` на `: ` во всех 18 вызовах `UserEvent(...)`.
4. **`ORIGINAL_PHONE` устанавливался без `__`-префикса.**
   `[sub-media]` выполняется не на канале `dialer_bridge`, а на канале,
   который порождает `Dial()` (через опцию `U()`), — Asterisk копирует
   в новый канал только переменные с префиксом `_`/`__`. Обычная
   переменная, установленная на канале-инициаторе, туда не попадает,
   поэтому `${ORIGINAL_PHONE}` в каждом `UserEvent(DialerResult,...)`
   внутри `[sub-media]` был всегда пуст — включая реальные звонки на
   реальный транк, это не артефакт тестового стенда. Исправлено:
   `Set(ORIGINAL_PHONE=${EXTEN})` → `Set(__ORIGINAL_PHONE=${EXTEN})`.

Все четыре бага исправлялись и проверялись по цепочке, а не по
отдельности: после каждого фикса файл копировался в работающий
контейнер (`docker cp` + `docker restart`/`dialplan reload` — пересобрать
образ не вышло, см. ограничение прокси в §1.4), размещался новый
тестовый звонок через реальную структуру AMI-экшена
`originate_call()`, и результат сверялся напрямую в Postgres. Итоговая,
финальная проверка (звонок на `79993334422`, кампания 7): в
`call_results` появилась строка `campaign_id=7,
phone=79993334422, status=timeout` — то есть весь путь
Asterisk-события → `handle_ami_event` → `_handle_user_event` →
`_save_call_result` → INSERT в Postgres теперь действительно работает,
с правильными данными, что не подтверждалось ни разу раньше. `status=
timeout` — реальный, ожидаемый исход в тестовом стенде: дозвон
подключался к `[test]`-контексту (`Answer()+Echo()`) вместо настоящего
SIP-транка, поэтому IVR не получал DTMF от абонента и упирался в
таймаут; это не баг, а следствие отсутствия настоящего транка в
песочнице (см. заметку про `FREEPBX_IP` выше в этом разделе).

**Пятый баг того же раунда (найден отдельно, исправлен следующим
раундом): дубли по числу gunicorn-воркеров.** Backend запускается через
`gunicorn -w 4`, и все 4 воркера независимо логинились в AMI под одним и
тем же аккаунтом `autodialer` — Asterisk рассылает каждое событие всем
подключённым менеджерам, поэтому каждое реальное AMI-событие
обрабатывалось (и сохранялось в `call_results`) 4 раза, по одному разу
на воркер — `processed_events` дедуплицирует только в рамках одного
процесса, не между ними. Остальные фоновые задачи в `DialerManager` уже
используют лидер-элекцию (`app/utils/leader_election.py`, тот же Redis
`SET NX`-механизм, что и у периодических воркеров в `app/workers/
__init__.py` — см. лог запуска `лидер: True/False`), но она не была
применена к самой обработке AMI-событий.

Исправлено: `DialerManager` теперь заводит собственный
`LeaderElection(lock_key="ami_event_processor")`, фоновая задача
`_maintain_event_leadership()` (по образцу `leader_wrapper` из
`app/workers/__init__.py`) раз в 5с пытается захватить лидерство, если
ещё не лидер, а `handle_ami_event()` в самом начале проверяет
`self._event_leader.is_leader` и молча выходит, если это не так —
событие AMI по-прежнему приходит на соединение каждого воркера, но
реально обрабатывает (и пишет в БД/публикует в Redis) только текущий
лидер. При `disconnect()` лидерство явно отдаётся, чтобы другой воркер
подхватил его сразу, не дожидаясь TTL (30с). Живая проверка: до фикса —
один реальный `UserEvent(DialerResult,...)` от Asterisk давал 4 строки в
`call_results` (по одной на воркер, тот же `linked_id`, все с
одинаковыми `created_at` до миллисекунд); после — ровно 1 строка на
событие (проверено запросом `SELECT id, campaign_id, phone, status,
linked_id, created_at FROM call_results WHERE phone=...` — id 47/48 в
таблице ниже соответствуют двум *разным* реальным `DialerResult`
событиям с разницей в 10с, а не дублям одного и того же).

Регрессионные тесты: `tests/test_dialer.py` (диспетчеризация
`handle_ami_event` по `event.event`, не `.name`; дедупликация по
`event`+`uniqueid`; новый тест — `handle_ami_event` ничего не делает, если
`_event_leader.is_leader` ложно) и `tests/test_dialplan.py` (статическая
проверка `extensions.conf` — `Key: Value` вместо `Key=Value` во всех
`UserEvent(...)`, `__ORIGINAL_PHONE` вместо `ORIGINAL_PHONE`).

### 1.5 Второй раунд живой проверки: DialBegin/Hangup никогда не
разрешали action_id, а звонки размещались строго по одному

Продолжая проверку "install → start → звонок → принят → записан",
следующим шагом было убедиться, что не только `UserEvent(DialerResult)`
(§1.4), но и весь остальной событийный конвейер (`DialBegin`,
`BridgeEnter`, `Hangup` — живая трассировка состояния звонка,
WebSocket-события `dial_begin`/`answer`, корректная очистка после
хангапа) реально работает на настоящем звонке, а не только на бумаге.
Не работал — и не мог работать, по совершенно отдельной причине от
всего найденного в §1.4. Найдено и исправлено ещё пять багов, один из
которых, скорее всего, самый серьёзный из всех обнаруженных в этом
проекте: **дозвонщик мог разместить только один звонок за раз,
строго последовательно** — то есть "авто"дозвонщик физически не мог
дозваниваться параллельно, вне зависимости от `max_calls`/CPS.

**Баг №1 (главный по важности): `DialerManager._start_call()` блокировал
единственный `queue_worker()` на 10+ секунд на КАЖДОМ звонке.**
`await self.manager.send_action(action)` для Originate с `'Async':
'true'` был обёрнут в стандартный вызов panoramisk без `as_list=False`.
Собственная эвристика `panoramisk.actions.Action.multi` (когда `as_list
is None`) считает ответ, заканчивающийся на "successfully queued"
(именно так отвечает Asterisk на асинхронный Originate), началом
многосообщенческой последовательности и не резолвит future, пока не
придёт ЕЩЁ и событие `OriginateResponse` — а оно для Originate,
маршрутизируемого через dialplan (не через `Application`), приходит
только когда выполнение dialplan на этом канале доходит до точки
завершения, что может быть сравнимо с длительностью всего звонка.
Живьём измерено: без `as_list=False` — `await send_action(...)`
резолвился через **10.5 секунды**; с `as_list=False` — **0.000 секунды**.
Поскольку `queue_worker()` делает `await self._start_call(...)` прямо в
своём единственном цикле, это означало, что **вся очередь дозвона
обрабатывалась строго последовательно**, по одному звонку каждые 10+
секунд, — при `max_calls=50` система физически не могла разместить
больше ~6 звонков в минуту, что делает предиктивный/параллельный
дозвон невозможным в принципе, независимо от всех остальных настроек.
Исправлено: `self.manager.send_action(action, as_list=False)`.

**Баг №2: `response.get('response')` падал, когда panoramisk всё же
складывал ответ Originate в список.** Даже независимо от Бага №1,
код читал `response.get(...)` напрямую, без нормализации через уже
существующий в файле `ami_response_events()` — если panoramisk
возвращал список (что и есть штатное поведение при multi-ответе),
это падало с `AttributeError: 'list' object has no attribute 'get'`,
что автоматически трактовалось как проваленный Originate: писался
фиктивный результат `originate_failed`, слот резервирования
освобождался, пока звонок на самом деле продолжал идти на стороне
Asterisk. Исправлено использованием `ami_response_events(response)[0]`
как источника истины по факту принятия экшена (реальный исход звонка
в любом случае отслеживается отдельно, через события `DialBegin`/
`DialerResult`, а не через этот ответ).

**Баг №3: `_start_call()` при успешном Originate регистрировал
буквально no-op (`self._add_mapping(action_id, None, None)` — оба
аргумента `None`).** `DialBegin`/`Hangup` никогда не несут заголовок
`ActionID` (подтверждено живым захватом сырых AMI-событий — Asterisk
не пробрасывает ActionID экшена на события, порождённые `Dial()`
внутри dialplan'а), так что `_resolve_action_id()` не имел вообще
никакого способа связать unique_id только что дозвонившегося канала
с action_id, который его разместил. Живьём это выглядело как
"DialBegin без ActionID" на КАЖДОМ реальном звонке и, каскадно,
"Невозможно разрешить ActionID" (CRITICAL) на КАЖДОМ Hangup — то есть
live-трассировка состояния звонка (`DIALING`/`ACTIVE`/`HANGUP`),
публикация `dial_begin`/`answer` в WebSocket и корректная очистка
после хангапа не работали ни для одного реального звонка в истории
проекта. Исправлено: `_start_call()` теперь регистрирует
детерминированный ПРЕФИКС имени канала (`Local/{номер}@dialer_bridge`,
без dial-опций вроде `/n`) в новом `self.action_to_channel_prefix`
ДО отправки Originate (не после — см. Баг №4); `_resolve_action_id()`
получил новый параметр `channel` и сопоставляет реальное имя канала
(Asterisk дописывает к нему `-XXXXXXXX;N`) с этим префиксом через
`startswith()`. Безопасно от коллизий, потому что `CHECK_PHONE_LUA`
уже гарантирует не больше одного активного звонка на нормализованный
номер одновременно — тот же номер, что и в префиксе.

**Баг №4 (гонка, найдена уже после фикса Бага №3): регистрация
префикса ПОСЛЕ `await send_action(...)` — гонка с самим Asterisk.**
Даже после Бага №3 часть `DialBegin` по-прежнему не резолвилась —
Asterisk может начать выполнять dialplan и прислать `DialBegin` по
тому же AMI-соединению раньше, чем наш собственный `await
send_action(...)` успеет обработать ответ и зарегистрировать mapping.
Исправлено переносом регистрации префикса до отправки экшена — она не
зависит ни от чего, кроме уже известных на этот момент
`action_id`/номера телефона.

**Баг №5 (архитектурный, всплыл при размещении нескольких звонков
одновременно): mapping'и — состояние в памяти ОДНОГО процесса, а
`queue_worker()` гоняется за `BLPOP` на всех 4 воркерах gunicorn
независимо.** Даже после Багов №3-4 звонки по-прежнему в основном не
резолвились — потому что `_start_call()` (который СОЗДАЁТ mapping)
мог выполниться на ЛЮБОМ из 4 воркеров (какой первым выиграет `BLPOP`
у Redis), а `handle_ami_event()` (который ЧИТАЕТ mapping) после
фикса дублей по воркерам (см. ниже) обрабатывает события только на
ТЕКУЩЕМ ЛИДЕРЕ. Если это разные процессы — а так происходит в 3 из 4
случаев — mapping просто не существует в памяти того процесса,
который получает события. Исправлено: `queue_worker()` теперь тоже
работает только на лидере (`_event_leader.is_leader`), не только
`handle_ami_event()` — так процесс, который размещает звонок, и
процесс, который потом читает по нему события, гарантированно
совпадают. Заодно это устраняет и скрытый разнобой в подсчёте
занятости (`local_active_estimate`/`cps_limiter`), который раньше
дрейфовал независимо в каждом из 4 процессов.

**Баг №6 (найден при повторной проверке после Багов №1-5, косвенный
побочный эффект собственного фикса из §1.4): дублирующийся заголовок
`Channel:` в `UserEvent(DialerHangup,...)` ронял обработку события.**
Фикс `=` → `: ` в §1.4 сделал `Channel: ${CHANNEL}` реальным
AMI-заголовком — но у ЛЮБОГО AMI-события (включая `UserEvent`) уже
ЕСТЬ собственный нативный заголовок `Channel:`, который Asterisk
добавляет всегда. `panoramisk.message.Message.from_line` при
СТРОГО одинаковом (регистрозависимо) имени заголовка дважды в сыром
тексте события хранит его как СПИСОК, а не строку — живой захват
подтвердил: `Channel: ['Local/...;2', 'Local/...;2']` (одно и то же
значение дважды). `channel.startswith('Local/')` в
`handle_ami_event()` падал с `AttributeError: 'list' object has no
attribute 'startswith'` на КАЖДОМ `DialerHangup`-событии — событие
терялось целиком, ничего не обрабатывалось. (Поле `LinkedID:
${CHANNEL(linkedid)}` той же коллизии не создаёт: сравнение в
`from_line` регистрозависимое, а нативный заголовок — `Linkedid`,
не `LinkedID`, так что просто тихо перезаписывается тем же
значением, без ошибки.) Исправлено: убран избыточный `Channel:`
из `UserEvent(DialerHangup,...)` в `asterisk/extensions.conf` (он и
так дублировал уже существующий нативный заголовок); дополнительно
`handle_ami_event()` теперь защищается нормализацией `channel` в
строку, если он всё же пришёл списком — на случай, если тот же класс
коллизии однажды вернётся через другое поле.

**Итоговая живая проверка всех шести фиксов вместе**: размещено 4
звонка одновременно одним `RPUSH` в `dial_queue` (тот же путь, что
использует продакшен-код, а не сырой AMI-скрипт в обход очереди) —
очередь опустела за **0 секунд** (была бы ~40+ секунд без Бага №1),
все 4 `📞 Originate OK` залогированы в одну секунду, ни одного
"DialBegin без ActionID" для реального unique_id, ни одного
"Невозможно разрешить ActionID", ни одного падения — и в
`call_results` появились строки с правильными `campaign_id`/`phone`/
`status` для всех четырёх звонков.

Регрессионные тесты в `tests/test_dialer.py`: `_start_call` вызывает
`send_action(..., as_list=False)`; `action_to_channel_prefix`
регистрируется ДО отправки Originate (не после); `_resolve_action_id`
резолвит по префиксу канала для свежего unique_id и не резолвит по
чужому префиксу; `queue_worker()` не трогает `BLPOP`/`_start_call` на
воркере, который не лидер; `handle_ami_event` нормализует
списочный `channel` в строку.

### 1.6 Третий раунд: `BridgeEnter` ("абонент ответил") работает, но
запись результата падала на гонке при upsert контакта

Продолжая ту же проверку — теперь уже конкретно "звонок принят"
(`BridgeEnter`/`✅ Абонент ответил`, то самое событие "ответил абонент",
о котором явно просил пользователь) — живьём подтверждено, что после
фиксов §1.5 оно действительно срабатывает и корректно резолвит
`action_id` через новый механизм префиксов. Но тут же, на том же
звонке, вскрылся отдельный, ранее не находившийся баг записи
результата:

**Баг: `CallResultService.save_call_result()` создавал контакт через
`SELECT`-затем-`INSERT` без какой-либо защиты от гонки.** Поскольку
`dialer_bridge` из-за флага `/n` выполняется дважды на звонок (по разу
на каждую половину Local-канала — см. §1.4/§1.5), два
`UserEvent(DialerResult,...)` для одного и того же номера телефона
почти неизбежно приходят и сохраняются в БД в пределах миллисекунд
друг от друга. Оба видят "контакта ещё нет" (SELECT ничего не находит),
оба пытаются `INSERT` — второй гарантированно падает: `duplicate key
value violates unique constraint "idx_contacts_phone_active"`.
Подтверждено живьём на реальном звонке через `dial_queue`. Исправлено
заменой на один атомарный `INSERT ... ON CONFLICT (phone) WHERE NOT
blacklisted DO UPDATE SET updated_at = NOW() RETURNING id` —
`idx_contacts_phone_active` (`sql/schema.sql`) это ЧАСТИЧНЫЙ
уникальный индекс (`WHERE NOT blacklisted`), и Postgres принимает
partial index как arbiter для `ON CONFLICT` только если предикат
совпадает буквально.

Заодно найден и исправлен тот же класс бага в соседнем, менее часто
используемом коде — fallback-пути `DialerManager._save_call_result()`
(срабатывает, только если `call_result_service` не задан): там ЕСТЬ
`ON CONFLICT (phone) DO UPDATE ...`, но без предиката `WHERE NOT
blacklisted` — без него Postgres вообще не принимает партиальный
индекс как arbiter и падает с "there is no unique or exclusion
constraint matching the ON CONFLICT specification" на любой
конфликт. Исправлено добавлением того же предиката.

Оба фикса проверены напрямую через `psql` (два одинаковых upsert подряд
для одного номера — оба успешны, оба возвращают один и тот же `id`) и
живым звонком через реальный `dial_queue`: `✅ Абонент ответил` и
`Результат звонка сохранён` для одного и того же номера теперь проходят
оба, без единой ошибки БД.

Регрессионные тесты: `tests/test_contacts_upsert.py` — статические
проверки исходного текста (по образцу `test_dialplan.py`), закрепляющие
атомарный `ON CONFLICT` в обоих местах; живая БД в этой песочнице не
настроена под тестовый прогон, поэтому SQL-корректность проверялась
живьём через `psql`, как описано выше.

### 1.9 Очередь повторных звонков: один баг исправлен и подтверждён,
второй — найден, но НЕ решён (честно не решён)

Проверяя, что происходит после `_schedule_retry()` (§3.3 старого плана,
статусы `busy`/`noanswer`/`failed`), нашлось два независимых бага в
`app/workers/retry.py: process_retry_queue()` — фоновой задаче, которая
раз в 10с должна поднимать из `campaign_contacts` контакты с истёкшим
`next_retry_at` и повторно звонить.

**Баг №1 (исправлен и подтверждён живьём): несуществующая колонка
`updated_at`.** `campaign_contacts` (см. `sql/schema.sql`) имеет только
`created_at`, а не `updated_at` — `UPDATE campaign_contacts SET
next_retry_at = NULL, updated_at = NOW() ...` падал с `column
"updated_at" of relation "campaign_contacts" does not exist` на КАЖДОЙ
попытке обработки очереди повторов, то есть **очередь повторных звонков
не обработала ни одного контакта ни разу за всю историю проекта**.
Исправлено удалением `updated_at = NOW()`. Проверено живьём: контакт с
`next_retry_at` в прошлом теперь корректно захватывается (`FOR UPDATE
SKIP LOCKED`) и `next_retry_at` очищается без ошибки — раньше вся
транзакция падала на этом месте.

**Баг №2 (НЕ решён — честно задокументировано, не выдаётся за
исправленное): `dialer_service.start_call()` зависает навсегда при
вызове именно из этой фоновой задачи.** После фикса Бага №1 обработка
доходит до размещения звонка — и виснет замертво. Не падает, не
логирует ошибку, просто никогда не возвращается. Диагностировано очень
подробно, с инструментированием кода построчно прямо в живом
контейнере:

- Зависает на самой ПЕРВОЙ команде Redis внутри `start_call()`
  (`await self.redis.is_blacklisted(...)`) — подтверждено пошаговым
  логированием каждой строки метода.
- Даже голый `await self.redis.client.ping()`, обёрнутый в СОБСТВЕННЫЙ
  `asyncio.wait_for(..., timeout=3)`, ни разу не сработал по таймауту
  ни разу за 5+ минут ожидания — то есть зависание не реагирует даже на
  отмену через `asyncio.wait_for` на уровне самого зависшего вызова.
- Исключены: удержание открытого соединения с Postgres на время вызова
  (переструктурировано так, чтобы соединение освобождалось ДО вызова
  `start_call()` — зависание осталось тем же); общий circuit breaker
  (`set_circuit_breaker()` не вызывается вообще нигде в проекте, то
  есть у `ConnectionPool` и `RedisClient` `_circuit_breaker` всегда
  `None` — мёртвый код, не может быть причиной).
- Процесс работает под `uvloop` (подтверждено, установлен и активен) —
  известный источник трудноуловимых взаимодействий `asyncpg`/
  `redis.asyncio` именно в контексте фоновых задач, но это гипотеза, не
  подтверждённая до конца.
- **Это НЕ зависание всего воркер-процесса**: HTTP `/api/health` на том
  же самом воркере отвечал нормально (~80мс) всё время, пока конкретная
  эта задача висела — зависла именно ОДНА эта корутина/таск, не весь
  event loop процесса.
- **Но зависает НАВСЕГДА именно периодический цикл retry_queue этого
  воркера.** `simple_wrapper()` (`app/workers/__init__.py`) крутит
  `while True: await func(); ...; await asyncio.sleep(interval)` — раз
  `await func()` (то есть `process_retry_queue()`) никогда не
  возвращается и не поддаётся отмене, этот `while True` для ЭТОГО
  конкретного воркера дальше первого зависания вообще не продвигается.
  Подтверждено логами: воркер, который захватил зависший звонок,
  переставал логировать свои 10-секундные циклы совсем, тогда как
  остальные 3 воркера продолжали работать независимо. То есть после
  первого попадания под этот баг один из 4 воркеров необратимо теряет
  способность обрабатывать retry_queue до перезапуска процесса —
  остальные 3 по-прежнему могут (если самим не попадётся тот же баг на
  своём звонке).
- Попытка защититься `asyncio.wait_for(dialer_service.start_call(...),
  timeout=15)` в `process_retry_queue()` **тоже не сработала** — ни
  разу не залогировалась ошибка таймаута за 5+ минут ожидания. Оставлена
  в коде как разумная защитная практика по аналогии с остальными
  AMI-вызовами в проекте (`Ping`/`CoreShowChannel` уже обёрнуты в
  `asyncio.wait_for`), но это НЕ подтверждённое решение — честно
  зафиксировано как всё ещё открытая проблема.
- Для полной диагностики нужна task-aware интроспекция (например,
  `py-spy dump` с поддержкой asyncio-тасков) — обычный `py-spy dump` в
  этой песочнице показывает только простаивающий event loop в
  `epoll_wait`, а не то, какая конкретно корутина зависла (`py-spy`
  установлен на хосте, `pip install py-spy` внутри контейнера не
  работает — та же проблема с прокси, что и при сборке образов).

**Итог**: очередь повторных звонков теперь как минимум не падает и
корректно забирает контакты из БД (Баг №1), но реальное размещение
повторного звонка через `dialer_service.start_call()` из этого
конкретного фонового контекста всё ещё не работает — контакт
захватывается (`next_retry_at` очищается), но звонок физически не
размещается, что означает **этот конкретный retry молча теряется**
(не крутится в цикле бесконечно, но и не размещается). Это следующий по
важности пункт для дальнейшей работы — нужна более глубокая асинхронная
диагностика, которой не было в этой песочнице.

Регрессионный тест: `tests/test_retry_queue.py` (статически закрепляет
Баг №1 — SQL-запрос `UPDATE campaign_contacts` не должен ссылаться на
`updated_at`). Регресс-теста на Баг №2 нет — нечего закреплять, пока
сам баг не исправлен.

### 1.10 Архитектурный вопрос: можно ли доверять статусу "дозвонились",
и подключение AMD как независимой проверки

Возник обоснованный вопрос: почему дозвон идёт через AMI, если FreePBX
как промежуточное звено (B2BUA) теоретически может отдавать нечестный
сигнал ответа — либо намеренно (провайдер шлёт "fake early answer" ради
биллинга), либо потому что мы на самом деле видим сигнал от транка до
FreePBX, а не от реального абонента. Отдельно — беспокойство, что
автоответчик засчитывается как "дозвонились", а сброс звонка абонентом
может неверно классифицироваться как ответ.

Разбор показал: смена локального API, которым бэкенд говорит с
Asterisk (AMI → ARI → свой SIP-клиент на pjsua2), сама по себе НЕ решает
проблему честности сигнала — FreePBX как хоп никуда не девается ни при
одном из трёх вариантов, и `200 OK` в стандартном SIP всегда
end-to-end от реального устройства, если только оператор осознанно не
подделывает supervision-сигнал. Это разные, не связанные друг с другом
проблемы: (а) какой локальный API дергает Asterisk — не влияет на
честность сигнала от оператора; (б) действительно ли оператор/FreePBX
шлёт честный ответ — проверяется независимо от (а), например живым
SIP-трейсом или независимым от SIP-сигнализации способом определения
"человек взял трубку", то есть AMD (анализ живого аудио) и DTMF.

Из трёх вариантов (полная миграция на ARI; свой SIP-клиент на pjsua2 —
недели-месяцы работы; подключить уже существующий, но неиспользуемый
`AMD()` + живой SIP-трейс на реальном звонке как проверка) выбран
третий — наименее рискованный, не требующий переписывания движка
дозвона, и единственный, который можно частично проверить прямо в этой
песочнице.

**Что сделано:** в `[sub-media]` (`asterisk/extensions.conf`) перед
запуском собственного TTS добавлен `Gosub(sub-amd,s,1)` — контекст
`[sub-amd]` уже существовал в коде (использует `AMD()`, сам шлёт
`UserEvent(DialerResult,Status: machine,...)` при вердикте MACHINE), но
никогда не вызывался ни из одного места дозвона. Теперь при вердикте
MACHINE звонок сразу уходит на `Hangup()` вместо того, чтобы
проигрывать питч на автоответчик; при HUMAN/NOTSURE — идёт как раньше
(NOTSURE намеренно трактуется как HUMAN, чтобы не терять реальных
абонентов на пограничных случаях).

Второе: `amd.conf` (настройки таймингов AMD) никогда не был версионирован
ни для одного из двух путей развёртывания — молча наследовался из того,
что установит пакет `asterisk` в конкретной ОС. Создан
`asterisk/amd.conf` со стоковыми значениями Asterisk (не откалиброван
под реальный русскоязычный автоответчик/приветствие — это отдельная
задача на будущее, когда появится образец реального трафика) и подключён
явно в обоих путях: `docker/asterisk/Dockerfile` (`COPY`) и
`scripts/03_asterisk_config.sh` (`cp`, bare-metal).

Третье, обнаружено попутно: bare-metal путь развёртывания
(`scripts/05_dialplan_config.sh`) генерирует СВОЙ независимый dialplan
через bash heredoc и не получил ни одного из более ранних фиксов этой
сессии (`Key=Value` → `Key: Value` в `UserEvent`, `__ORIGINAL_PHONE`,
дублирующийся `Channel:`-заголовок) — то есть два пути развёртывания
разошлись, и bare-metal нёс те же баги, что Docker-путь уже исправил.
Применены те же фиксы к `scripts/05_dialplan_config.sh` для паритета
между путями, плюс то же подключение AMD.

**Проверено живьём (Docker-путь, через реальный `dial_queue`, временно
переключив `Dial(${TRUNK_NAME}/${EXTEN},...)` на `Dial(Local/100@test,...)`,
т.к. реального транка/абонента в песочнице нет):**
`Gosub(sub-amd,s,1)` действительно выполняется, `AMD()` реально
анализирует (тишину — `100@test` это просто `Answer()+Echo()`) в течение
полных `total_analysis_time` (5000мс), корректно ветвится по
`GotoIf($["${AMDSTATUS}"="MACHINE"]?amd_hangup)` (в данном случае
вердикт NOTSURE → идёт по ветке `human`, `amd_hangup` не срабатывает —
что и ожидалось для голой тишины без структуры "приветствие+пауза"),
`Return()` возвращает выполнение обратно в `[sub-media]`, и дальше
`Background()`/`WaitExten()` отрабатывают как раньше. Ни одного падения
или необработанного исключения ни в Asterisk-логе, ни в бэкенд-логе;
`DialBegin`/`Hangup`/сохранение результата звонка (`failed`, т.к. DTMF
не пришёл — ожидаемо для теста без реального аудио) отработали как
обычно. После проверки временное переключение на `Local/100@test`
отменено, `extensions.conf` в контейнере возвращён к продовому
`Dial(${TRUNK_NAME}/${EXTEN},...)`.

**Что осталось непроверенным (честно, а не выдаётся за готовое):**
реальная точность AMD (отличит ли он настоящий человеческий "алло" от
настоящего автоответчика с приветствием) не проверена и не может быть
проверена в этой песочнице — нет ни реального транка, ни образца
реального приветствия автоответчика. Значения в `amd.conf` — это
стоковые дефолты Asterisk, не откалиброванные под русскоязычный трафик.
Вторая половина выбранного пути — снятие живого SIP-трейса на реальном
звонке через реальный FreePBX/оператора, чтобы увидеть, что они
реально шлют (честный `200 OK` от абонента или подделанный ранний
ответ) — не выполнена и не может быть выполнена отсюда: нет доступа к
реальному FreePBX/транку. Это следующий шаг, который может сделать
только тот, у кого есть доступ к боевому окружению — например, снять
`sngrep`/`pcap` на SIP-трафике FreePBX во время реального дозвона и
сверить с тем, что видит AMI (когда AMI шлёт `DialBegin`/`BridgeEnter`
относительно момента реального `200 OK` в трейсе).

Регрессионных тестов на сам факт вызова `Gosub(sub-amd,s,1)` из
`[sub-media]` нет (дозвон — это Asterisk dialplan, не Python-код;
статическая проверка синтаксиса `.conf`-файла проверяется через
`bash -n` для генерирующих его bare-metal скриптов, а сам dialplan —
только живым тестом, который выполнен выше).

### 2.1 Структура каталогов

```

  api/           REST-роутеры (health, auth, campaigns, contacts, calls, audio,
                 blacklist, users, settings, audit, incoming, websocket) + system
  services/      бизнес-логика; один файл на домен, ServiceRegistry + get_X_service()
  workers/       фоновые asyncio-задачи (retry, transcription queue, health monitor,
                 log cleanup, metrics, reconciliation), leader election через Redis
  utils/         circuit breaker, rate limiter, leader election, task registry
alembic/         миграции (одна на сегодня: 0001_initial_schema, читает sql/schema.sql)
sql/             schema.sql (эталон схемы), migrations/ (историческая последовательность,
```

### 2.2 Ключевые архитектурные решения и почему

- **Слой доступа к БД — asyncpg напрямую, не SQLAlchemy ORM**, несмотря
  на то, что ТЗ перечисляет SQLAlchemy в стеке. `app/core/database.py`
  — это готовый, полнофункциональный `ConnectionPool` + `QueryBuilder` +
  `BaseRepository` с health-check/reconnect, Circuit Breaker,
  Prometheus-метриками — уже написанный с расчётом на низкую задержку
  при сотнях одновременных запросов (важно для дозвонщика). Переписывать
  ~15 сервисов на ORM ради формального соответствия строке в ТЗ означало
  бы рискованный рефакторинг бизнес-логики без возможности его
  полноценно перепроверить в оставшееся время. Вместо этого SQLAlchemy
  используется **только** внутри Alembic (`alembic/env.py`) для
  управления миграциями — задача, для которой он и предназначен, без
  необходимости заводить ORM-модели. Если ORM обязателен по формальным
  причинам — это отдельная, крупная задача на будущую фазу (см. §3.6).
- **Фоновые задачи — свои asyncio-воркеры с leader election через Redis,
  не Celery**, хотя ТЗ говорит "Celery или аналог" (аналог — это ровно
  то, что уже было реализовано: `app/utils/leader_election.py` +
  `app/workers/__init__.py: start_all_workers()`). Один процесс, без
  отдельного брокера задач, что для дозвонщика с низкой требуемой
  задержкой между шагами кампании — разумный выбор. `celery[redis]`
  убран из зависимостей как неиспользуемый.
- **Веб-интерфейс остаётся vanilla JS**, а не переписан на React — это
  сознательный компромисс по приоритету "рабочее ядро сначала",
  выбранному в начале сессии. `frontend/dist/js/*.js` — рабочий,
  вызывает реальные `/api/*` эндпоинты (не статический макет), поэтому
  admin-panel уже пригодна к использованию, просто не на стеке из ТЗ.

Система работает как SIP UA через связку **наш Asterisk (в

также транслируется через WebSocket (канал `system`) при каждом
изменении статуса подключения/отключения AMI (см. §3.4).

## 3. Что осталось (по фазам, в порядке приоритета)

### 3.0 Критично: расхождение схемы БД и сервисного слоя — блокирует часть API
Найдено при написании юнит-тестов для `BlacklistService` (см. §3.3): моки
БД в юнит-тестах не проверяют реальные имена колонок, поэтому баг
вскрылся только когда сервис был прогнан против настоящего Postgres.

**Баг №1 (исправлен, широко распространён): `request.<enum>.value` при
`use_enum_values=True`.** `app/models/common.py: BaseSchema.model_config`
задаёт `use_enum_values=True` для вообще всех Pydantic-моделей проекта —
это значит, что поле-enum после валидации хранит **строку** (`request.reason
== "spam"`), а не объект enum. Написанный ранее код сервисов почти
везде обращался к этим полям как к enum-объектам: `request.reason.value`,
`filter_params.status]` в списковых включениях `[s.value for s in
filter_params.status]` и т.п. — рабочий с реальным enum, но кидающий
`AttributeError: 'str' object has no attribute 'value'` на голой строке.
Итог: `BlacklistService.add_to_blacklist()`/`bulk_add_to_blacklist()`
падали на **каждой** попытке добавить новый номер (до записи в БД —
`.value` вычислялся прямо в аргументах `INSERT`), `export_to_csv()` падал
при непустом списке. То же самое обнаружилось (grep по всем
`app/services/*.py` + точечная проверка каждого случая, живая ли это
enum-переменная или поле pydantic-модели) в: `app/services/audio.py`
(генерация TTS), `app/services/audit.py` (экспорт в CSV/JSON),
`app/services/call_result.py` (сохранение результата звонка — **самый
частый** путь записи в системе), `app/services/campaign.py` (создание/
обновление кампании), `app/services/contact.py` (создание/обновление
контакта, импорт), `app/services/incoming.py` (обновление входящего
звонка), `app/services/user.py` (создание/обновление пользователя,
кастомные разрешения). Исправлено везде одинаково: убран `.value` там,
где значение уже строка (поле pydantic-модели), оставлен там, где это
действительно объект enum (например, `CampaignStatus.RUNNING.value` —
прямое обращение к члену класса enum, не поле модели, не тронуто).
Регрессия зафиксирована тестами (`tests/test_blacklist_service.py`,
15 тестов, все через реальные `BlacklistAddRequest`/`BlacklistBulkAddRequest`
— то есть проходят валидацию `use_enum_values=True` так же, как в проде).

**Баг №2 (исправлен): `is_expired` — `None` вместо `False`.**
`app/services/blacklist.py: _get_blacklist_by_id()`/`list_blacklist()`
вычисляли `is_expired=row['expires_at'] and row['expires_at'] <
datetime.utcnow()` — при `expires_at IS NULL` (подавляющее большинство
записей: постоянная блокировка без срока) `and` возвращает `None`
(короткое замыкание), а не `False`, что валится на Pydantic-поле
`is_expired: bool`. Исправлено оборачиванием в `bool(...)`.

- **Проверено вживую**: `alembic upgrade head` с нуля (`0001→...→0009`),

### 3.4 SIP/AMI: живые события в WebSocket — сделано
**Важная поправка задним числом (см. §1.4):** на момент написания этого
раздела `handle_ami_event()` содержал баг (`event.name` вместо
`event.event`), из-за которого AMI-события никогда не долетали ни до
`_publish_call_event(...)`, ни до самой публикации в
`ws_channels:call`/`ws_channels:system` — то есть код ниже был написан
и выглядел правильно, но живьём никогда не выполнялся. Баг найден и
исправлен позже, при попытке проверить полный цикл "звонок → принят →
записан в БД" (см. §1.4). Описание архитектуры ниже остаётся верным
как есть — оно просто ранее не подтверждалось живым прогоном, только
чтением кода.

`DialerManager` теперь публикует `LiveCallEvent` (dial_begin/answer/
hangup/dtmf) и `SystemNotificationEvent` (подключение/потеря AMI) в
Redis-каналы `ws_channels:call`/`ws_channels:system`, которые уже
рассылались `WebSocketService` подключённым клиентам — раньше эти
AMI-события двигали только внутреннюю state machine, дашборд же видел
лишь статичный снимок при подключении.

Заодно исправлен фронтенд-клиент дашборда
(`frontend/dist/js/system.js`): он стучался в несуществующий
`/api/ws/system` с придуманным форматом сообщения, которого бэкенд
никогда не отдавал. Переключён на реальный `/api/ws/dashboard` и
разобранный по факту контракт `{"type": "call"|"campaign"|"system"|
"notification", "data": {...}}` из `app/api/websocket.py`. Также
исправлено чтение `data.asterisk_connected` в `refreshStatus()` —
такого поля REST `/system/status` никогда не возвращал (реальное имя

`CampaignService.start_campaign()` (`dial_task()`) теперь тоже
публикует `CampaignProgressEvent` в канал `campaign` — раз в 5
обработанных контактов, плюс всегда на завершение/остановку/ошибку
кампании — переиспользуя уже существовавший `get_campaign_progress()`.

Заодно найден и исправлен смежный баг: `_add_contacts_to_campaign()`
при добавлении контактов через `group_ids` выполнял
`conn.fetchval("SELECT COUNT(*) FROM ...")` — буквальное многоточие
вместо реального запроса, что гарантированно кидало бы синтаксическую
ошибку Postgres при каждой попытке добавить контакты в кампанию по
группам. Исправлено на разбор command-тега `INSERT N M`, который уже
возвращает `conn.execute()` (по аналогии с разбором `DELETE N` в
`remove_contacts_from_campaign`).

Заодно найдены и исправлены два смежных бага, из-за которых сама

### 3.7 Резервное копирование — сделано (bare-metal + Kubernetes; для docker-compose — вручную по образцу)
Реализовано для обоих путей развёртывания, упомянутых в ТЗ:

- **Bare-metal**: `scripts/15_backup_setup.sh` (по образцу существующих
  `scripts/07_postgresql_setup.sh`/`14_logrotate_setup.sh` — тот же стиль
  логирования, идемпотентности через маркер-файл, чтения `.env`)
  устанавливает `/usr/local/bin/autodialer-backup` (запускается по cron,
  расписание — `BACKUP_SCHEDULE` из `.env`, по умолчанию выключено —
  `AUTO_BACKUP_ENABLED=false`, эти переменные уже были в
  `.env.example`, но нигде не читались) и
  `/usr/local/bin/autodialer-restore <TIMESTAMP> [--yes]`.
  `autodialer-backup` делает `pg_dump -Fc` (custom-формат — нужен для
  `pg_restore --clean`), архивирует `tts_audio`/`call_recordings` через
  `tar` (пропускает, если каталог пуст/не существует), затем ротирует
  файлы бэкапов старше `BACKUP_RETENTION` дней (по умолчанию 30 —
  отдельная настройка от `settings.audio_retention_days`, та относится к
  самим аудиофайлам системы, не к их бэкапам). `autodialer-restore`
  восстанавливает БД и оба каталога из конкретного бэкапа, с
  подтверждением (`yes`/`no`, если не передан `--yes`), останавливая и
  перезапуская `autodialer.service` вокруг восстановления БД.

  **Проверено вживую в этой сессии** (в отличие от большей части
  Kubernetes/Docker-путей, см. §1.4): поднят нативный Postgres 16,
  выполнен `autodialer-backup`, затем данные в БД и оба каталога
  намеренно испорчены (удалена строка настройки, удалены файлы),
  `autodialer-restore <TS> --yes` восстановил всё побайтово (сверено
  напрямую через `psql`/`diff`-сравнение содержимого файлов). Отдельно
  проверена ротация: файл с `mtime` 40 дней назад корректно удалён при
  `BACKUP_RETENTION=30`, свежие — нет. Единственный найденный при
  тестировании нюанс (не баг, а ожидаемое поведение `tar x`): восстановление
  каталога не удаляет файлы, появившиеся в нём после бэкапа и отсутствующие
  в архиве — как `rsync` без `--delete`. Для `tts_audio`/`call_recordings`
  это не проблема (лишний файл не мешает), но стоит иметь в виду.

- **Kubernetes**: `k8s/50-backup-cronjob.yaml` — два `CronJob`
  (`media-backup` запускается на 15 минут позже `postgres-backup`, чтобы
  не претендовать одновременно на один и тот же PVC) пишут в отдельный
  `backup-storage` PVC (`ReadWriteOnce`) по той же логике, что и
  bare-metal скрипт (`pg_dump -Fc` + `tar` + ротация по `mtime`).
  Восстановление сознательно НЕ автоматизировано как `Job` — только
  задокументированная в комментариях файла процедура (`kubectl cp` +
  `pg_restore`/`tar x` через одноразовый под), по той же причине, что и
  `autodialer-restore` требует ручного подтверждения: восстановление —
  разрушительная операция, для которой автоматический безусловный запуск
  скорее опасен, чем полезен. Как и остальной `k8s/` (см. §3.5), **не
  применялось на реальном кластере** — только синтаксическая проверка
  YAML и extraction+`sh -n` проверка встроенных shell-команд. Честно
  задокументировано, что PVC-бэкап — это защита от случайного удаления/
  плохой миграции, а не полноценный disaster recovery (бэкап и данные на
  одном и том же storage backend); шаг с копированием вовне кластера
  (rclone/`aws s3 sync` и т.п.) не реализован.

- **docker-compose**: отдельного скрипта не заводилось — `docker-compose.yml`
  даёт прямой доступ к контейнеру Postgres, поэтому та же логика
  переносится однострочно: `docker compose exec -T postgres pg_dump -U
  $DB_USER -Fc $DB_NAME > backup.dump` из обычного cron на хосте (плюс
  `tar` volume-директорий `tts_audio`/`call_recordings`, которые в
  docker-compose и так смонтированы с хоста — см. `docker-compose.yml`).
  Не показалось оправданным дублировать почти идентичный скрипт в третий
  раз ради одного `docker compose exec` — `scripts/15_backup_setup.sh`
  можно использовать как образец логики ротации/восстановления один в
  один.

### 3.8 Стратегия масштабирования воркеров — аудит: заявленная проблема не подтвердилась
Воркеры (`start_all_workers()`) выполняются в том же процессе, что и API,
с leader election (`app/utils/leader_election.py`) для задач, которые не
должны дублироваться. Эта секция раньше утверждала, что `retry_queue`,
`transcription_queue` и `health_monitor` не leader-gated и потому будут
выполняться избыточно при горизонтальном масштабировании backend
(`replicas: 2+`). Аудит кода показал, что для всех трёх (и заодно
`metrics`) отсутствие leader election — не проблема, а корректный дизайн:

- `process_retry_queue` (`app/workers/retry.py`) забирает строки через
  `SELECT ... FOR UPDATE SKIP LOCKED` внутри транзакции — стандартный
  Postgres-паттерн безопасной конкурентной очереди: при N репликах каждая
  берёт непересекающееся подмножество строк, дублирования повторных
  звонков не происходит.
- Воркер `process_transcription_queue` из `worker_configs`
  (`app/workers/transcription_queue.py`) саму транскрибацию не делает —
  он раз в 5с проверяет размер очереди и пишет debug-лог. Реальная
  обработка — в `TranscriptionService._process_transcription_queue()`
  (`app/services/transcription.py`), которая читает задачи через
  `redis.blpop()` (атомарная операция — каждую задачу заберёт ровно один
  consumer), тоже безопасно при любом числе реплик.
- `health_monitor` и `update_metrics_periodically` не трогают разделяемое
  состояние — каждый отражает здоровье/метрики своего собственного
  процесса. Их не нужно (и не следует) leader-gate'ить: в
  Prometheus-модели каждая реплика обязана публиковать свои метрики
  независимо, иначе `/metrics` пустых реплик будет вводить в заблуждение.

Итого настоящих кандидатов на leader election изначально было верно
определено три: `cleanup_audio`, `log_cleanup`, `asterisk_reconciliation`
(синхронизация каналов с единственным инстансом Asterisk — гонка при
нескольких репликах) — все три уже leader-gated (`requires_leader=True`
в `worker_configs`, `app/workers/__init__.py`). Больше переносить нечего;
специального Worker-деплоймента или перехода на Celery для этого не
требуется.

Единственная реальная оговорка на будущее: если появится новая
периодическая задача с побочными эффектами на разделяемый ресурс (ещё
одна очередь без `SKIP LOCKED`/атомарного `BLPOP`), её надо либо сделать
leader-gated, либо явно спроектировать под конкурентных потребителей —
проверять это для каждой новой задачи отдельно, а не по умолчанию считать
дублирование воркеров проблемой.

### 3.9 Российский план нумерации — консолидация и фикс — сделано
Заказчик — из России, план набора должен быть российским (`+7`,
10 значащих цифр, мобильные коды `9XX`, домашний алиас `8` вместо `+7`).
Аудитом подтверждено, что это уже было заложено верно (`_X.` в
`asterisk/extensions.conf`/`asterisk.conf` — универсальный, без завязки
на другую страну; `pjsip.conf.template` уже `language = ru`; VOSK-модель
по умолчанию — `vosk-model-small-ru-0.22`) — но правила нормализации
(`8`→`7`, голый `9XXXXXXXXX`→`79XXXXXXXXX`, отображение
`+7 (900) 123-45-67`) были продублированы (с расхождениями) в 4 местах
бэкенда (`app/models/contact.py`, `blacklist.py`, `incoming.py`,
`app/services/dialer.py`) и в форматировании — ещё в 2
(`app/services/blacklist.py`, `app/services/call_result.py`).

Вынесены в единый `app/utils/phone.py`
(`normalize_phone`/`validate_phone_number`/`format_phone_display`), все
6+ дублей теперь импортируют/делегируют туда.

Заодно найден и исправлен реальный баг: валидатор
`CallResultCreateRequest.phone` (`app/models/call.py`) только вырезал
нецифровые символы, не приводя ведущую `8` к `7` — в отличие от всех
остальных телефонных полей в системе. Результат звонка с номером вида
`89991234567` сохранялся бы как есть, не совпадая с `contacts.phone`
(там всегда `79991234567`) при джойнах, и потенциально мог обойти
проверку чёрного списка. Исправлено на использование общего
`normalize_phone`.

`BlacklistAddRequest` заодно переведён с мягкой проверки `len(phone) >=
10` на общий `validate_phone_number()` — теперь так же отклоняет явно
некорректные коды оператора/региона (`70…`/`71…`), как и создание
контакта.

На фронтенде было 6 почти идентичных копий `formatPhone`/
`formatPhoneNumber` (`campaigns.js`, `blacklist.js`, `history.js`,
`contactGroups.js`, `dashboard.js`, `contacts.js`, плюс инлайновая в
`incoming.js`) — все переведены на делегирование к единственной
`App.formatPhoneNumber()` в `utils.js`. Заодно её ветка для голого
10-значного номера без кода страны исправлена, чтобы всегда показывать
`+7 (...)`, а не просто `(...)` без страны.

```bash
cp .env.example .env
# заполнить DB_PASSWORD, JWT_SECRET (32+ символов), AMI_PASSWORD,
# FREEPBX_IP/FREEPBX_EXTENSION/EXTENSION_PASSWORD
```

```bash
pip install -r app/requirements/base.txt -r app/requirements/dev.txt
alembic upgrade head
uvicorn app.main:app --reload
pytest tests/ -v
```
